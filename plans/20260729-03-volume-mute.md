# Plan: Volume & mute (milestone 3)

Add `POST /volume`, `POST /mute`, and `POST /unmute`. Small milestone,
**single PR against `main`** — the hard part (gain machinery) has existed
since milestone 2 phase 1: the player already reads `volume` and `muted`
from the shared status on every chunk and routes them through
`volume::gain()` / `volume::apply_gain()`. This milestone is the three
handlers, clamping at the API boundary, and tests.

## API

| Method & path  | Body              | Effect |
|----------------|-------------------|--------|
| `POST /volume` | `{"volume": 30}`  | Requested volume must be 0–100 (else 400). The stored value is `volume::effective_volume(requested, max_volume)` — a request above the cap is **clamped, never rejected**, and the response shows the effective value. |
| `POST /mute`   | —                 | `muted = true`. The volume value is untouched, so unmute restores it. |
| `POST /unmute` | —                 | `muted = false`. |

All three return the full status JSON (200), like `/play` and `/stop`.
Error semantics stay as established: malformed/missing body on `/volume` →
400 with `{"error": ...}`; wrong method/path → 404.

Range rule, spelled out: 0–100 is the request contract (mirroring the
config validation, which rejects `initial_volume > 100`); above `max_volume`
but ≤ 100 is a *valid* request that clamps silently. So with the default cap
of 50: request 30 → 30, request 80 → 50, request 101 → 400.

## Implementation

- Handlers only touch the shared `Mutex<Status>` — no player commands, no
  new state. The player picks the change up on the next chunk (~25 ms at
  44.1 kHz stereo), so volume/mute are effectively instant and work whether
  or not something is playing.
- Clamping happens in the handler via `volume::effective_volume()` — the
  same single function config loading uses. `status.volume` therefore always
  holds an *effective* (already-clamped) value, which is the invariant the
  player relies on.
- `server.rs` gets a `VolumeRequest { volume: u8 }` body type; serde
  rejects non-numbers and negatives for free (u8), the handler rejects
  101–255.

## Tests

- Routing: `/volume` below/at/above the cap (response shows the clamped
  effective value), 101 → 400, malformed bodies → 400, `/mute` → `muted:
  true` with volume untouched, `/unmute` restores, wrong methods → 404.
- End-to-end through the player (capturing `TestSink`, sine source): start
  playing, drop the volume via the route, assert the captured tail is
  scaled down accordingly; mute via the route mid-play → tail is silence;
  unmute → audio returns at the remembered volume.
- The existing invariant tests already pin the clamp itself; no changes to
  `volume.rs` are expected at all.

## Acceptance

- `cargo test` / `clippy` / `fmt` green on macOS and (via Docker) Debian.
- Manual on the Debian PC while music plays: `POST /volume {"volume": 10}`
  is audibly quieter within a blink; `{"volume": 100}` gets **no louder
  than the cap** (response says `"volume": 50`); `/mute` silences
  immediately; `/unmute` brings the music back at the pre-mute level.
