# Plan: async radiod on tokio (milestone 9)

- **Date:** 2026-08-01
- **Status:** approved; implemented in this stack
- **Order:** first of three (async → mixer ownership → AirPlay embed).
  Milestone 11 embeds the `openairplay2` library, whose `Receiver::run()` is
  async and runs on the **caller's** tokio runtime — this milestone creates
  that runtime and moves radiod's control plane onto it.

## Background

radiod today is fully synchronous: `tiny_http` serves the API on the main
thread, the player is an OS thread fed by `std::sync::mpsc`, and `ureq`
fetches playlists. That was the right shape for "play one stream to ALSA",
and CLAUDE.md codifies it ("no async runtimes").

The AirPlay work changes the calculus. The openairplay2 library's I/O is the
complicated half — a control connection that switches ciphers mid-stream, an
event channel, TCP/UDP audio channels — and it is tokio-native, validated
against real Apple senders. Porting *it* to threads would rewrite
hardware-validated code; porting radiod's simple control plane to async is
the smaller, safer move.

**What deliberately stays on OS threads:** the audio path. ALSA's blocking
`writei` *is* the pacing mechanism, and FFmpeg (libavformat) does its own
blocking network I/O internally. The player thread, the pipeline, and the
sinks do not become async — tokio owns the control plane, dedicated threads
own audio, channels bridge the two. (openairplay2 has the same split
internally: async protocol, dedicated playback thread.)

## Scope

In:

- A tokio runtime in `main`, **current-thread flavor** — the Pi Zero has one
  ARMv6 core; a multi-thread scheduler buys nothing. `spawn_blocking` still
  works (it uses the separate blocking pool).
- Replace `tiny_http` with an async HTTP server for the loopback API. Same
  routes, same JSON, same status codes — `notes/api.md` is the contract and
  does not change.
- Playlist resolution (`pls::resolve`, `ureq`) wrapped in `spawn_blocking` —
  not rewritten. It is one blocking fetch per `/play`; a reqwest migration is
  not worth the dependency.
- The player keeps its thread and its `std::sync::mpsc` command channel;
  async handlers `send()` into it exactly as the sync handlers do today
  (send is non-blocking).
- Graceful shutdown: `ctrl_c` → stop command to the player → sink closed —
  behavior we get mostly for free from tokio's signal handling.
- CLAUDE.md updates: amend the "no async runtimes" rule (control plane is
  tokio; audio stays on threads and blocking is still the pacing mechanism)
  and the approved-dependency list.

Out:

- Any change to the player, pipeline, sinks, volume path, or `/status`
  semantics. This milestone is a transport swap, not a redesign.
- The AirPlay integration itself (milestone 11).
- Avahi/mDNS (radiod doesn't advertise anything; the openairplay2 library
  handles its own advertisement later).

## Design notes

- **HTTP server choice:** `axum` is the pragmatic default (routing, JSON
  extraction, tiny handler surface — our API is ~8 routes). The lean
  alternative is raw `hyper`. Decide at phase 1 start; the deciding factors
  are ARMv6 binary size and compile time on the cross toolchain, both easy
  to measure with a spike commit. Either way `tiny_http` and its thread loop
  go away.
- **tokio features:** start from `rt`, `net`, `signal`, `sync`, `time`,
  `macros`. Milestone 11 will additionally need whatever `openairplay2`
  demands (`io-util`); fine to add then.
- **`Arc<Mutex<Status>>` stays.** It is held for microseconds by sync code;
  an async-aware lock buys nothing and would infect the player thread.
- The server tests in `server.rs` move from driving `tiny_http` directly to
  driving the async router (axum's `Router` is testable without a socket;
  with hyper we keep a real loopback listener).

## Phases

One stack: this plan as the bottom PR, then one branch/PR per phase stacked
on top, per house rules.

### Phase 1 — runtime + async API server

`#[tokio::main(flavor = "current_thread")]`; the HTTP server replaces
`tiny_http`; handlers call the unchanged `Player`/`Status`; `pls::resolve`
via `spawn_blocking`. All existing endpoint behavior preserved verbatim
(including the 409s and error JSON — the tests from milestones 3–4 are the
spec). CLAUDE.md dependency-policy update rides along.

### Phase 2 — shutdown + cleanup

Signal-driven graceful shutdown (player stopped, sink closed, exit 0);
remove `tiny_http`/dead code; confirm macOS `cargo test` and the wav/null
sinks still work; run on the Debian PC against real ALSA and on the Pi as a
`.deb` (cross-build unchanged).

## Decisions and findings (recorded during implementation)

- **HTTP server: raw `hyper`, not `axum`.** Beyond dependency size, the
  deciding argument is that `route()` already implements the whole API
  contract — including 404 (not 405) on wrong-method requests, which
  axum's router would fight — and the milestone 3–4 tests carry over
  nearly verbatim. Measured on the Debian PC: the release binary grows
  284 KB (4.33 MB → 4.62 MB) for tokio + hyper + hyper-util +
  http-body-util; axum would add tower/matchit on top of those same
  crates.
- **Shutdown waits on the status, not a thread join.** After the signal,
  main sends `Stop` and polls for `state == stopped` (5 s deadline)
  instead of joining the player thread — a join would require every
  `Player` clone (including ones held by lingering keep-alive connection
  tasks) to drop first. Status `stopped` implies the sink was closed, so
  the guarantee is the same.
- **Finding for milestone 10:** `AlsaSink` sets no buffer-size constraint,
  and on the Debian PC's HDA analog output the device ends up with a
  buffer so deep that `snd_pcm_drain` in `AlsaSink::close()` outlasts the
  5 s shutdown deadline (the daemon still exits 0 — the deadline exists
  for exactly this). Same pre-existing behavior means `/stop` and
  `/pause` keep playing buffered audio for seconds on such devices. Worth
  fixing in the ALSA-ownership milestone: constrain the buffer size in
  `open()` (and consider `drop()` instead of `drain()` for stop).

## Test strategy

- Every existing server test passes against the new server unchanged in
  *what* it asserts (route → status code → JSON body).
- New: a shutdown test (command channel closed → player thread exits, sink
  closed — the `TestSink` records `closed`).
- Hardware: install the `.deb` on the Pi; play/pause/volume from the
  website; memory footprint compared before/after (tokio on 512 MB should
  be fine, but measure, don't assume).

## Acceptance criteria

- `cargo test`, `clippy`, `fmt` green on macOS and Linux.
- API behavior byte-identical for the website's purposes (`notes/api.md`
  unchanged).
- Binary runs on the Pi Zero with no regression in idle CPU or startup time
  worth caring about (measure; a few MB more RSS is acceptable).
- CLAUDE.md reflects the new rule: async control plane, threaded audio.
